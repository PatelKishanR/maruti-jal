# Bilingual Support — English + Gujarati

The whole platform runs in either language, switchable from the topbar. This document defines what gets translated, what doesn't, and the specific technical traps that make Gujarati break silently if ignored.

---

## 1. The one rule

> **What the app says is translated. What you type is stored exactly as you typed it.**

Everything below follows from that sentence.

| Kind of text | Where it lives | Translated? |
|---|---|---|
| **What the app says** — labels, buttons, menus, validation messages, status names, report headings, empty states, KPI titles, confirmation dialogs | Message catalogues (`messages/en.json`, `messages/gu.json`) | ✅ Yes |
| **What you type** — product titles, staff names, addresses, notes, party names, walk-in names, coin type names, expense categories, product tags, filter types, price-override notes | Database, **one Unicode column each** | ➖ No. Stored as typed, shown as typed |
| **Codes and statuses** — `PARTIAL`, `REFUND_DUE`, `ORD-000123` | Database, always ASCII | ➖ Never store display text; translate at render |

---

## 2. No paired language columns

**There are no `*_en` / `*_gu` column pairs anywhere in the schema.**

A product has one `title`. A coin type has one `name`. An expense category has one `label`. Type it in whichever script you prefer, and it renders identically in both languages.

This is the right call because a 20-litre jar is the same jar whichever language the screen is in. Maintaining two names for one thing is data entry that earns nothing, and it creates a second problem the moment the two drift apart.

The seeded lookups — product tags (`Normal` / `Cold`), filter types (`Normal` / `Filtered` / `Double Filtered`), and the starter expense categories — ship in English and are fully editable. Rename them to Gujarati if you prefer, and that name is what everyone sees, everywhere.

## 3. Data entry

Every free-text field accepts Gujarati or English. PostgreSQL, trigram search and `ILIKE` are all Unicode-safe, so **no schema change is needed** to store Gujarati. Two rules make it actually work in practice:

### 3.1 No Latin-only validation patterns

**Never put a `[A-Za-z]` regex on any name, address, note or title field.** Validate on length only.

A leftover Latin-only pattern is the single easiest way to silently block Gujarati input, and it surfaces as "the app won't let me save" rather than as a validation bug. Phone numbers stay numeric-only; that constraint is legitimate.

### 3.2 ICU collation on name columns

The default PostgreSQL collation sorts by Unicode code point, which dumps every Gujarati name below every Latin one. A staff list sorted by name would show all English names, then all Gujarati names, rather than one sensible list.

Name and title columns therefore use an ICU collation (`gu-IN-x-icu`, supported on Neon) so mixed-script lists sort naturally.

### 3.3 Known limitation: search is script-literal

A staff member saved as `રમેશ` **will not** be found by typing `Ramesh`. A product saved as `૨૦ લિટર જાર` won't be found by typing `20L`.

Whichever script you use for a given kind of field, stay consistent.

If this becomes a real problem in daily use, the fix is an optional *"also known as"* alias column feeding the search index — additive, no rewrite, and crucially no second name to maintain on screen. It is deliberately not built now, because it may never be needed.

## 4. Numbers, money and dates

### 4.1 Latin digits, always

Figures stay in `0–9` in both languages. Indian lakh grouping is preserved in both (`₹12,34,567.00`).

This is a deliberate choice. Accounting software in India uses Latin digits because every cross-check the owner performs — against a register, a bank statement, a UPI app, a printed bill — uses Latin digits. Gujarati numerals would be visually consistent and operationally worse.

**This must be forced explicitly.** Requesting the `gu-IN` locale can produce Gujarati numerals depending on the runtime, so number formatting requests the Latin numbering system extension (`gu-IN-u-nu-latn`) rather than relying on defaults.

### 4.2 One choke point

All number, currency and date formatting goes through the shared money and date utilities. **No component calls the platform's `Intl` APIs directly.** That single choke point is what guarantees consistency across nine modules — otherwise one dashboard card eventually renders `૧૨,૩૪,૫૬૭` and nobody notices for a month.

### 4.3 Dates

Month names localise (`14 Aug 2026` / `14 ઑગસ્ટ 2026`) while the stored value stays the same `'YYYY-MM-DD'` string. **Locale affects display only** — never storage, never a date input's value, never anything sent back to the server.

## 5. Technical requirements

### 5.1 Locale handling

`next-intl` in its **"without i18n routing"** mode. Locale comes from a cookie plus the user's stored preference, and URLs stay clean (`/orders`, not `/gu/orders`).

For an internal tool with one user there is no SEO case for locale-prefixed routes, and skipping them avoids composing a second middleware with the auth middleware — a known friction point that costs more than it returns here.

The language switcher lives in the topbar. The preference is persisted to the user record and mirrored into a cookie, so the correct language renders on the very first server paint with no flash of English.

### 5.2 Message catalogues

Two files, `messages/en.json` and `messages/gu.json`, namespaced per module (`orders.*`, `coins.*`, `common.*`).

A CI check asserts **key parity** between them, so a new English string cannot ship without its Gujarati counterpart being at least present. Without that check, the Gujarati build degrades one missing string at a time.

### 5.3 Fonts — the trap that breaks Gujarati silently

**Inter has no Gujarati glyphs.**

Load **Noto Sans Gujarati** alongside Inter and place it in the sans-serif stack *after* Inter. Browsers fall back per character, so a line mixing `Ramesh` and `રમેશ` renders correctly in a single pass.

Without this you get tofu boxes or an inconsistent system fallback — and it presents as a data problem rather than a font problem, which is why it can survive weeks of testing.

### 5.4 Validation messages

Zod schemas define error **keys**, not sentences. The form layer resolves them through the active catalogue.

Otherwise a Gujarati UI returns English server errors — the exact seam where localisation usually leaks, because client-side validation looks perfect right up until the server rejects something.

### 5.5 Statuses stay ASCII in the database

Enum values are stored as `PARTIAL`, `REFUND_DUE`, `COMPLETE` and translated at render.

Display text is never stored. Equally, user-typed text is never translated.

## 6. Localised exports

Screens are the easy half. Documents are where Gujarati usually fails.

### 6.1 PDF

The generator must embed a **Gujarati-capable font subset**, or every Gujarati character renders as an empty box.

Gujarati also needs proper **complex-script shaping** for conjuncts and matras. Some PDF libraries position matras incorrectly even with the correct font loaded, producing text that is technically present but wrong to a reader.

**Verify this in Phase 1 with a real Gujarati name and address — not at the end of the project.** Discovering that the PDF library cannot shape Gujarati during the final week means replacing the export layer.

Affected documents: staff outstanding statement, party order statement, daily collection sheet.

### 6.2 CSV

Write UTF-8 **with a byte-order mark**.

Without the BOM, Excel on Windows shows mojibake for Gujarati while every other tool — Numbers, Sheets, a text editor, the terminal — looks fine. It therefore gets reported as "the export is broken" weeks later by whoever opens it in Excel first.

### 6.3 Content

Report headings, column labels and status values come from the catalogues, so a statement generated in Gujarati is fully Gujarati apart from codes and figures.

## 7. Layout

Gujarati strings run **longer and taller** than their English equivalents.

Sidebar labels, table headers, buttons, badges and KPI cards must not assume English string lengths. Fixed-width buttons and single-line table headers are the usual casualties.

**Every screen is checked in both languages before it ships.** Not at the end — as each module is built, because retrofitting flexible layouts across nine modules costs far more than getting each one right once.

---

## 8. Testing checklist

| Check | Why |
|---|---|
| Catalogue key parity in CI | Prevents the Gujarati build degrading one missing string at a time |
| No hardcoded user-facing strings | A lint rule catches what code review misses |
| Key screens snapshot in both locales | Catches layout breakage from longer Gujarati strings |
| A Gujarati staff name survives create → search → list → detail → edit | Proves the full Unicode path including trigram search |
| A Gujarati name and address in a generated PDF | Proves font embedding *and* complex-script shaping |
| A Gujarati CSV export opened in Excel on Windows | Proves the BOM is present |
| Money and dates render Latin digits in Gujarati mode | Proves the numbering-system extension is applied everywhere |
| Mixed-script sort order on the staff list | Proves the ICU collation is in place |
